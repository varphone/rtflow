# 0.3 → 0.4 迁移指南

0.4 是一次 minor 版本升级（0.x 语义下允许破坏性变更），重点是运行时基线更新、
TLS 后端收敛和 `--no-default-features` 构建修复。协议与公开 API 的语义保持不变。

## 最低 Rust 版本

MSRV 从 1.88 提升到 **1.95**。原因是最新依赖的硬性要求：

| 依赖 | 版本 | 要求 |
|---|---|---|
| `transmux` / `broadcast-common` | 0.33 / 14 | Rust 1.95 |
| `gstreamer` | 0.25.4 | Rust 1.92 |
| `rusqlite`（rtflow-server） | 0.43 | Rust 1.89 |

CI 的 MSRV 任务固定 `1.95.0`。使用 1.88–1.94 的项目需要先升级工具链。

才需要对齐版本。

## TLS：进程级 crypto provider

`reqwest` 改用 `rustls-no-provider`，以保持全工程单一 TLS 后端（ring）。
这意味着**创建 `reqwest::Client` 之前必须安装进程级 provider**：

- `rtflow-server` 的 `install_crypto_provider()` 已在 `ServerApp::start`、
  `HookClient::new` 中自动调用；
- `rtflow-onvif` 在创建 SOAP 客户端前自动调用；
- `rtflow-security` 的 TLS 配置构建函数显式安装 ring。

如果自行创建 `reqwest::Client`（例如在测试或自定义集成中），需要先调用：

```rust
let _ = rustls::crypto::ring::default_provider().install_default();
```

或直接调用 `rtflow_server::install_crypto_provider()`。

## 无默认特性构建

0.3 中 `cargo check -p rtflow --no-default-features --lib` 会失败：门面 crate
无条件导出了 `rtflow::http`、`rtflow::server` 与 `rtflow::protocols::hls`，
而它们是可选依赖。0.4 为这些导出补上了 feature 门控，因此：

- 只启用需要的 feature 时，未启用的模块不再存在（编译期错误而不是运行期缺失）；
- `embedded-gateway` profile 与 cargo-hack 的逐 feature 组合恢复可用。

升级后请按项目实际 feature 调整 `use rtflow::{http, server}` 等导入。

## 内置测试源（`test-source`）

0.3 的合成源在收到关键帧请求时跳到资产第 0 帧，之后按
`units % keyframe_interval` 继续取帧，可能**跳过中间帧**，使 AV1 等
带参考帧编码的码流失去参考链（dav1d 报 “Invalid data”）。0.4 改为强制关键帧后
从资产头部按序推进，关键帧间隔只在到期时重置 GOP。使用 `SyntheticSource` 的
测试/示例行为更稳定，API 未变。

## 升级检查清单

1. 工具链 ≥ 1.95（`rustc -V`）。
2. `cargo update` 后重新锁定依赖；直接依赖 `transmux`/`webrtc` 的项目对齐主版本。
3. 自建 `reqwest::Client` 的位置安装 crypto provider。
4. 按需调整 feature 组合，验证 `--no-default-features` 构建。
5. 用 FFmpeg/GStreamer 各跑一遍互操作（H.264/H.265/AAC + AV1/OPUS 等）。
